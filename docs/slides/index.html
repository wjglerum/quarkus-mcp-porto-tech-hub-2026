MCP moves fast  /  spec 2026-07-28

The newest spec drops the session

Until 2025-11-25

Session-based

Handshake first, then the server hands out a session id and remembers you.

2026-07-28

Stateless

No handshake, no session id. Every request says who it is and what it calls. Any server instance can answer.

Same gate on every request. No session means the token is the only identity.

60-second aside. Quarkus MCP Server 2.0 serves both modes on one endpoint; the demos use session clients (Inspector, LangChain4j). Details if asked: server/discover, MCP-Protocol-Version + Mcp-Method headers, client info in _meta. Any state handle must be bound to the token's sub.

What you just saw

Three boring acronyms, one secure flow

CIMD

Client ID Metadata Document

The client is a URL. No registration call, no manual setup per MCP server.

PKCE

Proof Key for Code Exchange

Stops stolen authorization codes from being usable.

Auth Code

Authorization Code Flow

User consents in the browser. App never sees the password.

How clients register

2026-07-28: CIMD is the default, DCR is deprecated

MethodHow it worksTrust anchorBest for
CIMD (recommended)client_id is an HTTPS URL; server fetches the JSON metadata on demandDomain ownershipOpen ecosystems, clients you don't control
Pre-registeredAdmin creates the client in the IdP ahead of timeExplicit, vettedFixed, known internal clients
DCR (deprecated)Client POSTs metadata to /register, gets a per-server client IDAnonymous / open endpointBackwards compatibility only

One URL beats a registration per server. The demo realm still has DCR wired up, and it took four policy changes to open that door.

If asked: 2026-07-28 also makes clients validate the iss parameter in the authorization response (RFC 9207, mix-up attacks).

Honest footnote

Propagate the identity, not the token

What you just saw

Token passthrough

One token, two audiences. Anything that holds it can call the API directly. The MCP spec says: MUST NOT.

The fix

Token exchange (RFC 8693)

The MCP server swaps my token for a new one: aud=conference-api, act=conference-mcp. The audit log names me and the agent.

Same user, narrower token per hop. Keycloak and Quarkus both support it.

Honest caveat

MCP standardises scope step-up (403). Assurance step-up via acr (RFC 9470) is our own contract, for now.

Beyond the token

OAuth answers who. It does not answer what the tool says.

Prompt injection

Data the AI reads can carry instructions. Keep sensitive tools behind a human confirmation.

Tool poisoning

Tool descriptions are prompts too. Pin and vet the servers you connect.

Least privilege

Small scopes per tool, step-up for the rest. A stolen token should be boring.

If you remember three things

Who.

Authenticated identity flows end to end. Not 'the AI did it'. Always a named user, propagated through every hop.

What.

Permissions are scoped and enforced at the server. The MCP tool is a thin door. The lock is yours.

Provable.

Every action is audited with the token claims that authorized it. Replayable. Reversible where it matters.

Your framework does the plumbing (here: Quarkus). You do the policy.
